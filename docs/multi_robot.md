# Face identities in a multi-robot deployment

The face gallery can be shared by several robots running on the same network. Each robot
still does all of its inference locally; only the **persistent identity knowledge** is
shared. This document describes the gallery, its profile scope, its provenance fields, how
to point the node at a shared database, and how concurrent enrolment is meant to behave.

## 1. What is persisted

`MongoFaceIdentityStore` (`face_recognition/identity_manager.py`) stores one document per
persistent identity:

```text
face_recognition_db.identity_database
{
  model_key:            "vggface2-aligned",   # the profile scope (see §2)
  unique_id:            "U15",
  creation_timestamp:   1758000000.0,
  last_seen_timestamp:  1758000042.0,
  total_detections:     421,
  good_samples:         96,
  confirmed:            true,
  quality_score:        0.87,
  custom_name:          "Pep",
  co_occurring:         ["U7"],
  embeddings:           [[...], ...],         # the diverse gallery, last N
  mean_embedding:       [...],
  updated_at:           1758000042.1,         # indexed: drives incremental refresh
  created_at:           1757999000.0,
  revision:             17,                   # $inc on every write
  created_by_robot:     "robot_a",
  updated_by_robot:     "robot_b",
  last_seen_by_robot:   "robot_b"
}
```

`U15` is **not** a person. It is a face profile. The canonical human identity
(`person_<uuid>`) belongs to `EutPersonManager` and links to this profile.

The node never queries or writes the gallery on the frame path: identities are loaded once
at startup and saved incrementally, throttled by `persist_every` /
`min_persist_interval` / `persist_flush_period`.

## 2. Profile scope

`model_key` is the profile scope. Embeddings generated by different models, crop modes,
alignment or input sizes are not comparable, so they must never share a gallery.

* Default (unchanged): `f"{face_embedding_model}-{crop_mode}"`, e.g. `vggface2-aligned`.
* Override: the `profile_scope` parameter, or `$FACE_PROFILE_SCOPE` when the parameter is
  empty. An explicit scope is what you want when a name must survive a change of a default,
  or when two robots must be pinned to the same gallery.

The store ignores and counts documents belonging to another scope
(`count_other_model_documents()`) and documents with no `model_key` at all
(`count_legacy_documents()`), and the node logs both counts. **Incompatible embeddings are
therefore never silently mixed**, and nothing is deleted when a scope changes.

Legacy documents (written before the `model_key` refactor) have no scope. They are ignored,
not migrated: the scope they were produced under cannot be reconstructed, so treating them
as a separate gallery is the only safe reading.

## 3. Provenance

Every write records which robot authored it:

* `created_by_robot` — set once, when the profile is first inserted (`$setOnInsert`);
* `updated_by_robot`, `last_seen_by_robot` — refreshed on every save;
* `revision` — incremented server-side (`$inc`), so two robots writing the same profile can
  never both read the same revision and lose an update.

Empty values mean "single robot" and are the default, so existing deployments are unchanged.

## 4. Remote database mode

Set either the parameter or the environment (the parameter wins):

```bash
FACE_DB_MONGO_URI="mongodb://eurecat:cerdanyola@identity-host:27018/?authSource=admin"
FACE_PROFILE_SCOPE="vggface2-aligned"
ROBOT_ID="robot_a"
```

The parameter surface is `mongo_uri` / `profile_scope` / `robot_id` in
`config/face_recognition_params.yaml`. URIs are deliberately *not* launch arguments: empty
values do not survive them, which is why they are parameter/environment-only (same
convention as `person_db_uri` in `EutPersonManager`).

Nothing else changes in remote mode — no code path, no topic, no message type.

## 5. Concurrent enrolment

Normal recognition stays local and fast:

```text
frame -> embedding -> local in-memory gallery -> match
```

Creating a **new** persistent identity is rare and is the only operation that needs care. Two
robots that both see the same new human and both decide to create a profile must not end up
with two global face profiles and two canonical persons.

* The gallery's `unique(model_key, unique_id)` index already prevents two documents for the
  same scope+id.
* Until identity allocation is moved to a shared atomic counter, `U<n>` is still derived
  from `max_user_number()` — so **two robots racing to bootstrap a brand-new gallery can
  still mint the same number**. In single-robot mode this is not reachable; when running
  several robots against one database, let one robot create the first identity, or wait for
  the shared allocator (planned, see `EutPerceptionStack/plan.md` phase 6).
* Ownership of a face profile (which `person_<uuid>` it belongs to) is decided by
  `EutPersonManager`, which performs the race-safe resolve-or-create. The face gallery never
  decides that.

## 6. Cross-robot refresh

Load is startup-only today. A robot that is already running does not yet see profiles another
robot enrolled afterwards; it will after a restart, and the periodic refresh that removes
that restriction is planned in `EutPerceptionStack/plan.md` phase 5. The `updated_at` index
and the `revision` field are already in place so that refresh can pull only what changed and
detect conflicting writers.
